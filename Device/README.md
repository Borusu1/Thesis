# Warehouse Device Firmware

Цей проєкт містить прошивку для `ESP32-S3` складського термінала. Це не просто демо NFC-рідер, а робочий пристрій, який:
- читає й записує NFC-мітки;
- працює з `TFT` дисплеєм;
- зберігає локальний стан на `microSD` у `SQLite`;
- виконує локальні складські операції;
- синхронізує дані з backend у хмарі.

Прочитавши цей файл, можна зрозуміти повний поточний цикл роботи пристрою.

## Апаратна конфігурація

Пристрій побудований на:
- `ESP32-S3`
- `TFT ILI9341`
- `PN532` по `SPI`
- `microSD`
- 3 кнопках: `Up / Down / OK`
- зеленому й червоному LED

## Роль пристрою в системі

Пристрій є `offline-first` складським терміналом.

Його задачі:
1. Provision NFC-міток.
2. Lookup мітки.
3. Локальний `Receipt`.
4. Локальний `Shipment`.
5. Збереження всіх операцій у локальну SQLite БД на SD.
6. Синхронізація з backend через Wi‑Fi.

## Як пристрій працює при старті

Після включення виконується `boot diagnostics`.

Перевіряються:
- `TFT`
- `Buttons`
- `PN532`
- `SD`
- `SQLite`

Якщо все добре:
- пристрій переходить у робоче меню.

Якщо якийсь модуль не піднявся:
- на екрані показується `FAIL`;
- система не переходить у нормальний режим.

## Ідентичність пристрою

Система працює за схемою `device-only`.

Це означає:
- жодних паролів;
- жодного operator PIN;
- жодного badge login.

Замість цього:
- `ESP32` використовує власний hardware id;
- backend сприймає його як `device_id`;
- усі синхронізовані операції журналюються як виконані цим пристроєм.

Тобто зараз видно:
- який пристрій зробив зміну;
- але не яка саме людина фізично тримала пристрій.

## Модель NFC-мітки

На мітці зберігається:
- `UUID` у `NDEF Text payload`.

Система також читає:
- фізичний `chip UID` самої NFC-мітки.

Це дає 2 рівні ідентифікації:
- логічна мітка: `tag_uuid`;
- фізичний чіп: `chip_uid_hex`.

## Поточна складська модель

На поточний момент діє така логіка:

- `1 NFC tag = 1 партія одного товару`
- кількість на мітці: від `1` до `99999`

Це означає:
- на одній мітці не одна одиниця товару, а lot;
- мітка представляє конкретний товар і поточну кількість;
- часткове відвантаження зменшує кількість на мітці;
- повне відвантаження закриває її usage.

## Головні режими роботи

### 1. Provision

Призначення:
- записати новий `UUID` на NFC-мітку.

Сценарій:
1. Користувач обирає `Provision`.
2. Прикладає мітку.
3. Пристрій генерує новий `UUIDv4`.
4. Записує його як `NDEF Text`.
5. Одразу reread-ить payload.
6. Якщо reread збігається, запис вважається успішним.
7. Потім пристрій намагається синхронізувати provision у backend.

Можливі стани:
- `written + synced`
- `written + queued`
- `conflict`
- `write failed`
- `verify failed`

Provision може виконувати `auto reissue`, якщо backend дозволяє перепризначення того самого фізичного чіпа.

### 2. Lookup

Призначення:
- прочитати мітку й показати її поточний стан.

Пристрій показує:
- `tag UUID`
- `chip UID`
- тип payload
- локальний / серверний складський стан
- товар
- поточну кількість

Типові результати:
- `Unknown tag`
- `Provisioned but not received`
- `Active`
- `Shipped / closed`

### 3. Receipt

Призначення:
- прив’язати товар і кількість до provisioned мітки.

Сценарій:
1. Обрати товар із локального списку recent products.
2. Ввести кількість у редакторі з `5` цифр.
3. Прикласти мітку.
4. Локально створити usage для цього товару.
5. Зберегти операцію в SQLite.
6. Одразу або пізніше синхронізувати її в backend.

Як працює ввід кількості:
- на екрані є `00000`
- `Up/Down` рухають фокус між цифрами і кнопкою `SAVE`
- `OK` на цифрі входить у режим редагування
- `Up/Down` змінюють поточну цифру `0..9`
- `OK` фіксує цифру
- `OK` на `SAVE` підтверджує кількість

### 4. Shipment

Призначення:
- зменшити залишок на мітці.

Сценарій:
1. Сканується мітка.
2. Пристрій показує поточний залишок.
3. Користувач вводить кількість до відвантаження.
4. Якщо введена кількість менша за поточну:
   - виконується `partial shipment`.
5. Якщо дорівнює поточній:
   - виконується `full shipment`.
6. Операція спочатку пишеться локально, потім синкається.

## Інтерфейс керування

Пристрій використовує тільки 3 кнопки:
- `Up`
- `Down`
- `OK`

Основні принципи:
- `Up/Down` пересувають фокус;
- `OK` підтверджує;
- довге натискання `OK` використовується як `back/cancel`.

## Екранна логіка

Ключові екрани:
- `Boot diagnostics`
- `Mode menu`
- `Lookup`
- `Receipt`
- `Shipment`
- `Provision`
- `Sync`
- `Diagnostics`

На дисплеї також показуються:
- статус мережі;
- статус API;
- `pending sync`;
- результат останньої операції.

## LED-індикація

Зелений LED:
- 1 блимання: успішне читання;
- 2 блимання: успішний provision.

Червоний LED:
- сигналізує помилку операції або sync.

LED не блимає постійно у фоні.

## Локальне зберігання

На `microSD` зберігається `SQLite` база:
- `/sd/warehouse.db`

У ній є:
- журнал подій пристрою;
- локальна модель тегів;
- локальний каталог товарів;
- локальні inventory operations;
- черга pending sync.

Це потрібно, щоб:
- переживати reboot;
- працювати при тимчасовій відсутності мережі;
- не втрачати операції.

## Синхронізація з backend

Пристрій працює як `offline-first`.

Логіка така:
1. Операція спочатку зберігається локально.
2. Якщо мережа доступна, пристрій намагається відправити її одразу.
3. Якщо мережа або backend недоступні:
   - операція лишається в `pending sync`.
4. Далі sync engine повторює спроби з backoff.

Синхронізуються:
- `provision`
- `receipt`
- `shipment_partial`
- `shipment_full`

Пристрій також підтягує з backend:
- `recent products`

## Порядок синхронізації

Важливий принцип:
- спочатку має пройти `Provision sync`;
- тільки після цього можуть іти `Receipt` і `Shipment` для цієї мітки.

Це потрібно, щоб backend уже знав про `tag_uuid` і `chip_uid_hex`.

## Wi‑Fi та cloud

Поточна прошивка вже налаштована на AWS backend:

Базові параметри:

Після boot пристрій:
1. підключається до Wi‑Fi;
2. робить `device auth`;
3. підтягує recent products;
4. синхронізує локальну чергу.

## Що зберігається на самій мітці

На мітці зберігається тільки:
- `UUID` у `NDEF Text`.

На мітці не зберігається:
- назва товару;
- кількість;
- історія;
- статус синхронізації.

Уся бізнес-інформація лежить:
- локально в SQLite;
- централізовано в backend.

## Локальна перевірка і збірка

Збірка:

```bash
python3 -m venv .venv
./.venv/bin/python -m pip install platformio
./.venv/bin/python -m platformio run -e esp32-s3-devkitc-1
```

Прошивка:

```bash
./.venv/bin/python -m platformio run -e esp32-s3-devkitc-1 -t upload --upload-port /dev/cu.usbmodem1101
```

```bash
c++ -std=c++17 -Iinclude test/native/device_core_tests.cpp -o /tmp/device_core_tests
```
